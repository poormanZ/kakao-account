# 서비스별 데이터 모델

## 1. 목적

`kakao-account`는 여러 서비스가 공통으로 사용하는 **계정/인증 플랫폼**이다. 따라서 서비스의 실제 도메인 데이터까지 계정 DB에 무분별하게 저장하지 않는다.

핵심 원칙은 다음과 같다.

- 계정 플랫폼은 사용자 식별, 인증, 세션, 공통 설정만 책임진다.
- 서비스 도메인 데이터는 각 서비스가 소유한다.
- 모든 서비스 데이터의 사용자 연결 기준은 `users.id`를 사용한다.
- `kakao_user_id`를 서비스 DB의 외래키나 비즈니스 식별자로 사용하지 않는다.
- 계정 삭제 시 계정 플랫폼이 보유한 데이터는 즉시 삭제하며, 서비스 데이터 삭제는 서비스별 삭제 계약을 통해 연계한다.

## 2. 데이터 소유 경계

```text
                    kakao-account
                         │
          ┌──────────────┴──────────────┐
          │                             │
       users                         sessions
          │
          └── user_settings

              서비스 A                  서비스 B
                 │                        │
          service-specific DB      service-specific DB
                 │                        │
             user_id ─────────────── users.id
```

### 계정 플랫폼이 저장하는 데이터

- `users`: 내부 사용자 ID와 최소한의 Kakao 매핑 정보
- `sessions`: 서비스 인증 세션
- `user_settings`: 계정 플랫폼 공통 설정

### 각 서비스가 저장하는 데이터

- 게임 진행도
- 결제/구독 상태
- 콘텐츠/프로젝트
- 서비스별 프로필
- 서비스별 통계 및 기타 도메인 데이터

서비스 도메인 데이터가 생길 때마다 `kakao-account`에 테이블을 추가하지 않는다.

## 3. 서비스 사용자 식별 계약

서비스는 인증된 요청에서 계정 플랫폼이 제공하는 내부 사용자 ID를 받는다.

예:

```json
{
  "user_id": 123
}
```

서비스 DB에서는 다음과 같이 `user_id`를 저장한다.

```sql
CREATE TABLE service_records (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_service_records_user_id
  ON service_records(user_id);
```

실제 서비스에서는 `service_records`라는 공통 테이블을 그대로 사용하지 않고 해당 서비스의 도메인 명칭과 컬럼을 정의한다.

## 4. API 경계

계정 플랫폼 API:

- 로그인
- 로그아웃
- 현재 사용자 조회
- 공통 사용자 설정
- 계정 삭제

서비스 API:

- 서비스별 CRUD
- 서비스별 권한
- 서비스별 비즈니스 로직
- 서비스별 데이터 보관/삭제 정책

계정 플랫폼은 서비스의 도메인 권한을 대신 판단하지 않는다.

## 5. 계정 삭제 연계

사용자가 `DELETE /api/account`를 실행하면 계정 플랫폼의 다음 데이터가 삭제된다.

1. `user_settings`
2. `sessions`
3. `users`

외부 서비스가 존재하는 경우에는 별도의 계정 삭제 연계 절차가 필요하다.

권장 방식:

1. 계정 플랫폼이 삭제 이벤트/콜백 계약을 제공한다.
2. 각 서비스가 자신의 `user_id` 데이터를 삭제한다.
3. 서비스가 삭제 완료를 확인한다.
4. 계정 플랫폼이 최종 삭제 상태를 기록할 필요가 있다면 별도 최소 감사 데이터만 보관한다.

현재 단일 서비스 단계에서는 별도 이벤트 시스템을 도입하지 않고, 서비스 추가 시 계약을 확정한다.

## 6. 왜 계정 DB에 JSON 하나로 저장하지 않는가

서비스 데이터를 `user_data` 같은 JSON 컬럼 하나에 모두 넣는 방식은 초기에는 단순하지만 다음 문제가 있다.

- 서비스별 스키마 검증이 어려움
- 인덱스/쿼리 최적화가 어려움
- 서비스 간 결합도가 증가함
- 데이터 삭제/보관 정책을 서비스별로 분리하기 어려움
- 계정 플랫폼 D1 사용량이 서비스 성장에 직접 영향을 받음

따라서 **계정 플랫폼과 서비스 데이터의 저장소/스키마 소유권을 분리**한다.

## 7. 확장 규칙

새 서비스가 추가될 때는 다음 순서를 따른다.

1. 서비스가 필요한 도메인 데이터를 정의한다.
2. 서비스 자체 DB에 테이블을 만든다.
3. 계정 플랫폼의 `users.id`를 서비스 사용자 식별자로 사용한다.
4. 서비스 API에서 인증된 `user_id`를 기준으로 권한을 검사한다.
5. 계정 삭제 연계 정책을 정의한다.
6. 계정 플랫폼에 서비스 전용 테이블을 추가하지 않는다.

## 8. 현재 결론

현재 `kakao-account` 단계에서는 새로운 서비스 전용 migration을 추가하지 않는다. 계정 플랫폼의 책임 범위를 계정/인증/공통 설정으로 고정하고, 실제 서비스가 추가되는 시점에 해당 서비스의 독립 데이터 모델을 설계한다.
