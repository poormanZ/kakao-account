# Escape Room 미니게임 제작 기획서

## 1. 게임 개요

### 1.1 제목
**ESCAPE ROOM : PRIME WORLD**

### 1.2 장르
- 웹 기반 방탈출 / 추리 / 퍼즐
- 4인 협동 플레이를 고려한 병렬 퍼즐 구조
- 스토리 중심의 단계형 퍼즐

### 1.3 핵심 콘셉트
플레이어는 갑작스럽게 정체불명의 이세계에 도착한다. 겉보기에는 평범하지만 곳곳의 숫자가 이상하다. 플레이어가 직접 숫자의 규칙을 발견하면서 이 세계가 **소수(PRIME NUMBER)를 기준으로 유지되는 세계**임을 알아낸다.

그러나 탈출을 위해서는 그 규칙을 따르는 것이 아니라, 오히려 규칙에서 벗어난 대상을 찾아야 한다.

> **이 세계의 규칙을 따르지 않는 존재만이 이 세계를 벗어날 수 있다.**

## 3. PHASE 0 — 이세계 도착 / 프롤로그

### 3.1 프롤로그 목적

게임 시작 직후 플레이어에게 퍼즐을 제공하기 전에 **현실에서 이세계로 이동하는 사건**을 짧은 영상과 텍스트로 보여준다.

프롤로그에서는 `PRIME`, `소수`, `숫자의 규칙` 등의 정보를 직접 설명하지 않는다. 플레이어가 평범한 퇴근길에서 비정상적인 상황으로 넘어왔다는 감각만 전달한다.

핵심 감정 흐름은 다음과 같다.

```text
평범한 퇴근
   ↓
갑작스러운 서비스 장애
   ↓
지친 상태로 막차 탑승
   ↓
잠깐의 수면
   ↓
이상한 정적
   ↓
벌레 울음 소리
   ↓
불이 꺼진 버스
   ↓
사라진 운전기사
   ↓
처음 보는 마을
   ↓
불이 켜진 빈 마을 회관
   ↓
"여기가 어디지?"
```

### 3.2 프롤로그 스토리

플레이어의 1인칭 또는 3인칭 시점으로 다음 내용을 전달한다.

> 오늘도 평범하게 네이버에서 일을 하고 있었다.
>
> 그런데 퇴근을 앞두고 갑작스럽게 서비스 장애가 발생했다.
>
> 장애 대응을 하느라 정신없이 시간을 보내고, 겨우 막차를 타고 퇴근할 수 있었다.
>
> 항상 타던 **7919번 버스**였다.
>
> 너무 피곤했던 탓인지 버스에 올라타자마자 자리에 몸을 맡겼다.
>
> 잠깐 눈을 붙인 것뿐이라고 생각했다.
>
> 얼마나 시간이 지났을까.
>
> 어디선가 들려오는 벌레 울음 소리에 눈을 떴다.
>
> 버스 안은 불이 모두 꺼져 있었다.
>
> 버스는 멈춰 있었고, 주변에는 아무도 없었다.
>
> 운전기사도 보이지 않았다.
>
> 피곤함에 잠에 취한 채 종점까지 온 것 같았다.
>
> 버스에서 내려 주변을 바라보았다.
>
> 그런데 익숙한 풍경이 아니었다.
>
> 처음 보는 마을이었다.
>
> 정거장 바로 앞에 작은 마을 회관이 보였다.
>
> 이상하게도 회관에는 불이 켜져 있었다.
>
> 하지만 안에는 아무도 없었다.
>
> 나는 잠시 망설이다가 회관 안으로 들어갔다.

### 3.3 프롤로그 연출

권장 영상 길이는 **20~30초** 정도로 짧게 구성한다.

화면은 현실적인 한국의 밤 풍경에서 시작해 점차 이질적인 마을 분위기로 바꾼다.

#### Shot 1 — 늦은 밤의 사무실

- 늦은 밤 사무실
- 모니터에 서비스 장애 대응 화면이 희미하게 보임
- 피곤한 직장인이 마지막 업무를 처리함
- 형광등과 모니터 불빛만 남은 분위기

#### Shot 2 — 막차 탑승

- 밤의 버스 정류장
- 버스 전면 또는 측면에 `7919`가 보임
- 급하게 버스에 올라탐
- 문이 닫히고 버스가 출발

#### Shot 3 — 잠드는 장면

- 버스 좌석에 기대어 눈을 감음
- 도시의 불빛이 창문 밖으로 흐름
- 화면이 점차 어두워짐
- 짧은 시간 경과 느낌

#### Shot 4 — 벌레 울음 / 이상한 정적

- 어두운 버스 내부
- 갑자기 주변 소리가 줄어듦
- 벌레 울음 소리가 들림
- 플레이어가 눈을 뜸
- 버스 실내등은 모두 꺼져 있음

#### Shot 5 — 빈 버스

- 정차한 버스
- 운전석에는 아무도 없음
- 승객도 없음
- 문이 열리고 바깥의 낯선 풍경이 보임

#### Shot 6 — 처음 보는 마을

- 밤의 낯선 시골 마을
- 버스 정류장 표지판
- 바로 앞에 불이 켜진 마을 회관
- 주변에는 사람이 없음
- 카메라가 회관을 천천히 바라봄

마지막 화면:

```text
마을 회관
불은 켜져 있었다.
하지만 아무도 없었다.
```

이후 화면 전환과 함께 실제 게임 플레이가 시작된다.

### 3.4 프롤로그 사운드

영상의 공포감을 과도하게 높이지 않고 **현실적인 불안감**을 만드는 방향으로 구성한다.

- 사무실: 키보드, 알림음, 컴퓨터 팬 소리
- 버스: 엔진음, 주행음, 차체 진동음
- 수면: 버스 주행음이 점차 작아짐
- 깨어남: 갑작스러운 정적 후 벌레 울음
- 빈 버스: 아주 약한 전기음 또는 바람 소리
- 마을: 귀뚜라미, 바람, 먼 거리의 자연음
- 회관: 문 여는 소리와 내부의 미세한 생활 소음

### 3.5 프롤로그 영상 제작 방법

비용과 제작 난이도를 낮추기 위해 **한 편의 긴 영상을 한 번에 생성하기보다 4~6개의 짧은 클립을 각각 생성한 뒤 편집하는 방식**을 권장한다.

```text

   +

   +
버스에서 잠드는 클립
   +

   +

   +
불 켜진 빈 회관 클립
   ↓
간단한 영상 편집
   ↓
20~30초 프롤로그
```

AI 영상 생성 프롬프트는 모든 장면에서 다음 공통 스타일을 유지한다.


### 3.6 프롤로그에서 주의할 점

- `PRIME`이나 `소수`를 영상에 노출하지 않는다.
- 숫자 `7919`는 현실 세계에서 평범한 버스 번호처럼 보이게 한다.
- 버스 번호를 지나치게 강조하지 않는다. 이후 스토리에서 다시 의미를 부여할 수 있다.
- 운전기사가 사라진 이유를 설명하지 않는다.
- 마을 회관에 사람이 없는 이유도 설명하지 않는다.
- 회관에 들어가는 순간부터 플레이어가 직접 조사하도록 한다.
- 공포 장르보다는 **현실에서 조금씩 어긋나는 미스터리**를 우선한다.

## 4. PHASE 1 — 문제 1: 노트북 로그인

문제 1은 **2개의 병렬 단서 카드**로 구성한다. 두 카드는 서로 다른 정보를 제공하지만 최종적으로 하나의 컴퓨터 로그인 정보를 완성한다.

### 4.1 카드 A — 색상 문장

카드에는 다음 문장이 적혀 있다.

> **Open our archive confirm performance.**

각 단어는 다음 색상으로 표시한다.

```text
Open        → 빨간색
our         → 파란색
archive     → 초록색
confirm     → 노란색
performance → 보라색
```

카드 하단에는 다음과 같은 5개의 색상 입력 슬롯이 있다.

```text
컴퓨터 아이디 :
[빨강] [파랑] [초록] [노랑] [보라]

컴퓨터 비밀번호 :
[빨강] [파랑] [초록] [노랑] [보라]
```

카드 A만으로는 숫자를 알 수 없으며, 카드 B의 Performance 그래프가 필요하다.

### 4.2 카드 B — Performance 그래프

두 번째 카드의 제목은 **Performance**이다.

그래프의 x축은 `1~12`이며, 소수 위치에서 성능이 크게 증가한다.

```text
x = 1  → 낮음
x = 2  → 높음 / 빨강
x = 3  → 높음 / 파랑
x = 4  → 낮음
x = 5  → 높음 / 초록
x = 6  → 낮음
x = 7  → 높음 / 노랑
x = 8  → 낮음
x = 9  → 낮음
x = 10 → 낮음
x = 11 → 높음 / 보라
x = 12 → 낮음
```

그래프의 색상 점은 `2, 3, 5, 7, 11`에만 표시한다. 그래프 아래에는 `2 / 3 / 5 / 7 / 11` 숫자 라벨을 별도로 표시하지 않는다. 플레이어가 **x축의 위치를 직접 읽어야** 한다.

특히 `x=3`의 점은 `x=2`보다 더 높은 값으로 표시하고, `x=12`는 다시 낮은 값으로 내려가도록 구성한다.

### 4.3 아이디 풀이

카드 A의 색 순서:

```text
빨강 → 파랑 → 초록 → 노랑 → 보라
```

카드 B에서 해당 색의 x값을 읽는다.

```text
빨강 → 2
파랑 → 3
초록 → 5
노랑 → 7
보라 → 11
```

아이디는 색상별로 대응하는 **소수의 이름을 사용**한다.

```text
PRIME
```

따라서:

```text
컴퓨터 아이디 = PRIME
```

### 4.4 비밀번호 풀이

같은 색 순서의 숫자를 그대로 이어 붙인다.

```text
빨강 → 2
파랑 → 3
초록 → 5
노랑 → 7
보라 → 11
```

따라서:

```text
2 + 3 + 5 + 7 + 11
= 235711
```

최종 로그인 정보:

```text
ID       : PRIME
PASSWORD : 235711
```

### 4.5 문제 1의 의도

문제 1에서는 게임이 시작하자마자 '소수'라고 알려주지 않는다.

플레이어가 다음 순서로 발견하도록 한다.

```text
색상이 있는 문장
      ↓
Performance 그래프 조사
      ↓
높은 점의 위치 확인
      ↓
2, 3, 5, 7, 11 발견
      ↓
소수라는 규칙 발견
      ↓
색상 ↔ 소수 연결
      ↓
PRIME / 235711 완성
```

### 4.6 웹 UI 구현 기준

첫 화면은 참고 카드 이미지와 같은 **두 장의 종이 카드 레이아웃**으로 구성한다.

- 좌측: 색상 문장 + 아이디/비밀번호 색상 입력선
- 우측: Performance 그래프
- 크림색/종이 질감 배경
- 얇은 검정 테두리와 모서리 장식
- 카드 상단/하단에 불필요한 `ESCAPE ROOM`, `CARD 01`, `PRIME WORLD` 등의 문구를 넣지 않는다.
- 그래프 하단의 `2, 3, 5, 7, 11` 숫자 라벨을 넣지 않는다.
- 모바일에서는 두 카드가 세로로 배치된다.

### 4.7 서버 검증

브라우저는 아이디와 비밀번호를 서버로 전달하고, 정답 판정은 Cloudflare Worker에서 수행한다.

```text
Browser
   │
   │ { id, password }
   ▼
Cloudflare Worker
   │
   │ server secret: ESCAPE_ROOM_KEY_1_1
   ▼
ACCESS GRANTED / ACCESS DENIED
```

서버 secret은 다음 형식으로 관리한다.

```text
ESCAPE_ROOM_KEY_1_1=PRIME|235711
```

클라이언트 JavaScript에는 최종 정답을 비교하는 로직을 넣지 않는다. 틀린 입력에 대해서도 예상 정답이나 부분 정답을 반환하지 않는다.

## 5. PHASE 2 — 문제 2: 10월 생일자 기록

문제 2는 **소수 여부를 직접 판별하는 숫자 퍼즐이 아니다.** 플레이어는 다이어리에서 찢어진 듯한 종이 한 조각을 발견하고, 그 종이에 적힌 `내생일`의 이름을 알아내는 것이 목표다.

### 5.1 시작 단서 — 찢어진 다이어리 페이지

방탈출 시작 후 방 안에서 다음과 같은 종이 조각을 발견한다.

```text
10월 생일자 목록

1009 — 김하나
1011 — 내생일
1013 — 박준호
1019 — 최서연
1021 — 한지우
1031 — 윤태호
```

페이지는 일반 문서가 아니라 **다이어리에서 찢어진 한 장**처럼 보이도록 제작한다.

핵심은 `1011 — 내생일`이라는 표기다.

```text
목표
1011 — 내생일
       ↓
     이름은 누구인가?
```

이 단계에서는 `1009`, `1011`, `1013` 등의 숫자를 소수/비소수로 판정해서 답을 찾지 않는다. 숫자는 생일을 특정하기 위한 기록으로만 사용한다.

### 5.2 방 조사 — 김하나의 생일 축하 롤링페이지

방 안의 컴퓨터 또는 다른 디지털 단서에서 **김하나의 생일 축하 롤링페이지**를 발견한다.

페이지 제목 예시:

```text
김하나의 생일을 축하해요!
```

롤링페이지에는 여러 사람이 작성한 생일 축하 메시지가 남아 있다.

작성자 예시:

```text
박준호
최서연
한지우
윤태호
송유라
```

### 5.3 축하 메시지 내용

각 메시지는 자연스러운 생일 축하 내용으로 구성하되, 송유라의 메시지만 **10월 생일이라는 공통점을 언급**한다.

예시:

```text
박준호
하나야 생일 축하해!
항상 밝은 모습으로 있어줘서 고마워!

최서연
생일 축하해 하나야!
올해도 하고 싶은 거 다 이루자!

한지우
하나야 생일 축하해!
늘 옆에 있어줘서 고마워 :)

윤태호
생일 축하해! 하나야
맛있는 거 많이 먹고 좋은 하루 보내!

송유라
하나야 생일 축하해!
우리 같은 10월 생일이라 더 반가워 ㅎㅎ
올해도 좋은 일만 가득하길! ♡
```

실제 구현에서는 여러 메시지가 한 화면에 보이도록 구성하되, 송유라의 메시지는 플레이어가 읽을 수 있도록 명확하게 표시한다.

### 5.4 이름 추론 과정

플레이어는 찢어진 생일자 목록과 롤링페이지의 작성자 목록을 비교한다.

생일자 목록에서 이미 이름이 공개된 사람:

```text
김하나
박준호
최서연
한지우
윤태호
```

롤링페이지의 작성자:

```text
박준호
최서연
한지우
윤태호
송유라
```

두 목록을 비교하면 **송유라만 생일자 목록에서 이름이 빠져 있다.**

그리고 송유라는 직접:

> **"우리 같은 10월 생일이라 더 반가워"**

라고 적었다.

따라서 플레이어는 다음과 같이 추론한다.

```text
송유라
   ↓
김하나와 같은 10월 생일
   ↓
10월 생일자 목록에는 송유라 이름이 없음
   ↓
'내생일'에 해당하는 이름
   ↓
송유라
```

최종 답:

```text
1011 — 송유라
```

### 5.5 문제 2의 핵심 설계 의도

문제 2에서는 플레이어가 이미 문제 1에서 발견한 PRIME 규칙을 무조건 적용하지 않도록 한다.

플레이어가 자연스럽게:

```text
찢어진 다이어리 페이지 발견
        ↓
'내생일'이라는 미완성 정보 확인
        ↓
방 안의 다른 기록 조사
        ↓
김하나의 생일 축하 롤링페이지 발견
        ↓
작성자 이름 비교
        ↓
송유라의 메시지 발견
        ↓
'우리 같은 10월 생일'
        ↓
생일자 목록에 없는 이름 확인
        ↓
1011 — 송유라
```

라는 탐색 과정을 경험하게 한다.

즉, 문제 2의 핵심은 **숫자 해독이 아니라 문서 간 정보 대조와 인물 추적**이다.

### 5.6 시각 자료

문제 2의 주요 단서는 다음 2장의 이미지로 제작한다.

**이미지 1 — 찢어진 다이어리 페이지**

- 오래된 다이어리에서 찢어진 종이 조각처럼 표현
- 제목: `10월 생일자 목록`
- `1009 — 김하나`
- `1011 — 내생일`
- `1013 — 박준호`
- `1019 — 최서연`
- `1021 — 한지우`
- `1031 — 윤태호`
- `1011 — 내생일`은 플레이어가 주목할 수 있도록 자연스러운 표시를 적용하되, 정답 이름을 직접 암시하는 장식은 사용하지 않는다.

**이미지 2 — 김하나의 생일 축하 롤링페이지**

- 컴퓨터/웹페이지 형태의 생일 축하 게시판
- 여러 사람의 축하 메시지 표시
- 작성자: 박준호, 최서연, 한지우, 윤태호, 송유라
- 송유라의 메시지에 다음 핵심 문장을 포함:
  `우리 같은 10월 생일이라 더 반가워 ㅎㅎ`
- 여러 메시지 중 송유라의 메시지를 읽으면 다른 자료와 비교할 필요성이 생기도록 구성
- 전체적으로 실제 친구들의 온라인 생일 축하 페이지처럼 자연스럽게 디자인

### 5.7 웹 UI / 인터랙션 기준

- 시작 시 찢어진 다이어리 페이지를 조사할 수 있어야 한다.
- 페이지 확대/열람 기능을 제공한다.
- 방 안에서 김하나의 롤링페이지 단서를 찾아 열람할 수 있어야 한다.
- 롤링페이지는 여러 메시지를 보여주며, 특정 메시지만 정답 힌트가 되도록 한다.
- 플레이어가 최종적으로 `송유라`를 입력하거나 선택하면 문제 2를 완료한다.
- 클라이언트에 정답 비교 로직을 하드코딩하지 않고 서버 검증 구조를 사용한다.

## 6. PHASE 2.5 — 송유라의 다이어리

문제 2에서 `1011 — 송유라`를 찾아낸 뒤, 플레이어는 방 안의 다이어리 주인을 특정할 수 있다.

송유라의 다이어리는 일반적인 개인 기록처럼 보이지만, 안쪽 첫 페이지에는 다음과 같은 문장이 적혀 있다.

> 나는 이곳의 사람이 아니다.
>
> 처음에는 나도 이곳이 이상하다는 것을 몰랐다. 하지만 이곳의 사람들은 숫자를 너무 당연하게 받아들인다.
>
> 날짜도, 물건도, 길도 모두 같은 규칙을 따른다.
>
> 이곳에서는 **소수가 특별한 숫자가 아니다.** 오히려 소수가 아닌 것이 이상한 것이다.
>
> 그리고 이 세계에는 네 가지 색의 돌이 있다.
>
> 사람들은 그것을 **사색석(四色石)**이라고 부른다.
>
> 붉은 돌, 푸른 돌, 초록 돌, 노란 돌.
>
> 이곳에서는 사색석을 화폐처럼 사용한다.
>
> 네 돌의 가치는 서로 다르며, 그 값 역시 이 세계의 규칙을 따른다.
>
> **2, 3, 5, 7.**
>
> 하지만 어느 색이 어느 숫자를 의미하는지는 기록되어 있지 않다.
>
> **저울이 진실을 알려줄 것이다.**

### 6.1 스토리 연결 의도

문제 2에서 발견한 `송유라`가 단순한 퍼즐 정답으로 끝나지 않고, 이후 세계관의 핵심 인물로 연결되도록 한다.

```text
1011 — 내생일
      ↓
롤링페이지 조사
      ↓
송유라 발견
      ↓
송유라의 다이어리
      ↓
"나는 이곳의 사람이 아니다."
      ↓
이방인의 정체 확인
      ↓
사색석 이야기
```

여기서부터 플레이어는 `1011`의 의미를 다시 생각하게 된다. 그러나 문제 2의 최초 풀이 단계에서는 소수 여부를 정답 근거로 사용하지 않는다.

## 7. PHASE 3 — 사색석 4인 병렬 퍼즐

4명의 플레이어가 동시에 서로 다른 장소의 단서를 조사하고 중앙에서 정보를 합친다.

```text
PLAYER A → 단서 A ┐
PLAYER B → 단서 B ├→ 중앙 저울 퍼즐
PLAYER C → 단서 C ┤
PLAYER D → 단서 D ┘
```

### 사색석

| 색상 | 이름 | 실제 가치 |
|---|---|---:|
| 🔴 붉은색 | 혈석 | 2 |
| 🔵 푸른색 | 청석 | 3 |
| 🟢 초록색 | 녹석 | 5 |
| 🟡 노란색 | 황석 | 7 |

토큰에는 숫자를 직접 표시하지 않는다.

### 단서 관계

```text
붉은 돌은 푸른 돌보다 가볍다.
초록 돌은 푸른 돌보다 무겁다.
노란 돌은 초록 돌보다 무겁다.
붉은 돌은 네 돌 중 가장 가볍다.
```

결과:

```text
붉은 < 푸른 < 초록 < 노란
```

후보 값이 `2, 3, 5, 7`이므로:

```text
붉은 = 2
푸른 = 3
초록 = 5
노란 = 7
```

실제 양팔저울과 숫자 추를 사용해 마지막으로 검증한다.

## 12. 퍼즐 설계 원칙

1. 답을 화면에 직접 노출하지 않는다.
2. 플레이어가 여러 단서를 연결해서 규칙을 발견하게 한다.
3. 문제 1은 2개의 카드로 분리하여 병렬 탐색을 유도한다.
4. 그래프는 소수 위치를 시각적으로 강조하지만 '소수'라는 단어를 먼저 알려주지 않는다.
5. 그래프 아래에 소수 숫자 라벨을 넣지 않아 x축 판독을 요구한다.
6. 문제 2는 숫자의 소수 여부를 정답 근거로 사용하지 않고, 문서 간 정보 대조를 통해 이름을 찾게 한다.
7. 문제 2의 `1011 — 내생일`은 이후 세계관의 핵심 단서가 되지만 최초 풀이에서는 숫자 규칙과 분리한다.
8. 카드와 문서 디자인은 실제 방탈출 인쇄물/디지털 기록처럼 자연스럽게 구성한다.
9. 정답 검증은 서버에서 수행하고 클라이언트에는 정답 비교 로직을 두지 않는다.
10. 프롤로그는 설명보다 분위기와 사건 전달에 집중하며, 세계의 숫자 규칙은 이후 퍼즐에서 처음 발견하게 한다.
11. 이후 단계에서 PRIME/NON-PRIME의 의미가 스토리와 직접 연결되도록 한다.

## 15. 핵심 테마 연결

```text
7919 = 현실에서 이세계로 넘어오는 출발점
1011 = 이 세계의 규칙을 따르지 않는 인물로 이어지는 단서
8121 = 이 세계의 규칙을 따르지 않는 버스
```
